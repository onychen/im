## 1. 项目全景与一分钟自述

### 1.1 这是什么

一个面向 Web 的完整即时通讯系统（私聊 / 群聊 / 好友 / 朋友圈 / 文件上传 + 实时 WebSocket）。

| 层 | 技术 | 职责 |
| --- | --- | --- |
| 前端 | React 19 · TypeScript 5.7 · Vite 8 · Tailwind 4 | SPA |
| 前端状态 | Zustand（会话态）+ TanStack Query（服务端态） | 双层状态 |
| 后端 | Go 1.24 · Gin 1.9.1 | REST + WS + 业务 |
| 实时 | gorilla/websocket 1.5.3 | 长连接 |
| 存储 | MySQL 8.4 | 持久化 |
| 缓存 | Redis 7.2 + Lua | 读模型 / 原子操作 / 消息总线 |
| 异步 | Kafka 3.7（KRaft）· segmentio/kafka-go | 持久化事件投递 |
| 交付 | Docker Compose · GitHub Actions · GHCR | CI/CD |

依赖清单见 `backend/go.mod:5-16`。**注意后端只用了这些直接依赖**，没有引入任何 IM 框架、没有 ORM（`database/sql` 手写 SQL）、没有 Redis 客户端封装层，可以说明技术选型克制。

### 1.2 一句话架构主张

> **「Redis 是消息系统的读写主模型，MySQL 只是它的异步归档，Kafka 负责把两者可靠解耦。」**

这是整个项目最值得讲的设计主线。传统做法是「MySQL 落库后推送」，本项目反过来：**消息先原子写进 Redis（客户端立刻可见、可同步），持久化事件经由 Redis Stream → Kafka → 消费者异步落 MySQL**。

- 收益：发送路径延迟从「DB 写入的 5–10ms」降到「一次 Redis Lua 往返的亚毫秒级」，实测 P50 **0.23ms**（`backend/docs/压力测试总结.md:121-128`）。
- 代价：Redis 与 MySQL 存在**短暂不一致窗口**，且引入了「Redis 必须持久化」这个新约束。这个取舍的完整论证见本文第 9.1 节。

### 1.3 版本演进线索（面试时可以讲「我改过什么」）

项目里保留了完整的设计与问题记录，能看出架构是**迭代出来的**，不是一次成型：

| 阶段 | 形态 | 证据 |
| --- | --- | --- |
| v1 | WS → 写 MQ → 消费者写 Redis + 推 WS + 落 MySQL | `consumer/private_msg_consumer.go`（仍在，作为回退路径） |
| v2（当前默认） | WS → **Lua 原子写 Redis + Stream** → relay → MQ 写入确认 → 推 WS → 消费者只落 MySQL | `internal/redis/lua_message_write.go`、`internal/relay/message_relay.go`、`consumer/message_persist_consumer.go` |
| v3 | MQ 从 RabbitMQ 迁移到 Kafka：confirm → `acks=all`，ack → 提交 offset，TTL+DLX → retry Topic | `internal/infra/kafka.go`、`consumer/kafka_runner.go`、`docs/Kafka迁移说明.md` |

切换由配置开关 `message.atomic_pipeline` 控制（`internal/config/config.go:46-50`、`cmd/server/main.go:125,154-159`），**支持回退**——这是很成熟的工程意识，面试时值得主动提。

### 2.1 依赖注入：纯手工，无框架

`cmd/server/main.go:51-233` 是完整的装配过程，顺序严格：

```
配置 → zap 日志 → signal.NotifyContext → MySQL → Redis → Kafka(带重试 + EnsureTopics)
  → 健康监控 StartHealthMonitor → 加载 Lua 脚本 → 构建 3 个 repo → 独立 relay Writer(可选)
  → ConnectionManager → 8 个 Service → MessageDispatcher → 8 个 Handler
  → setupRouter → 启动 5 个消费者 → 清理任务 → pprof → HTTP Server
```

**面试点**：为什么不用 Wire/Dig？因为依赖图虽然宽（约 20 个对象）但不深，手工装配的**显式性**更有价值——一眼能看出服务启动依赖了什么，排障时不用猜。

### 2.2 优雅退出与 MQ 故障策略

`main.go` 用 `signal.NotifyContext` 把 SIGINT/SIGTERM 变成 `ctx`，所有消费者、relay、健康监控都挂在这个 `ctx` 上，收到信号后统一退出并 `srv.Shutdown`。

**RabbitMQ 版本的做法**：同时监听 `ctx.Done()`、`mqFailure`（连接/通道 NotifyClose）、`relayPublishFailure` 三个退出源，MQ 一断就主动退出进程，让容器编排重启。原因是 amqp091-go 不自动重连，连接失效后进程会「僵尸运行」。

**Kafka 版本的做法**：kafka-go 的 Writer/Reader 自带断线重连和 leader 切换处理，所以删掉了「断连即退出」，改为 `StartHealthMonitor` 每 10s Ping 一次，`/ready` 据此返回 503，由负载均衡摘流量。消息不会丢：relay 写入失败就不 XACK，事件留在 Stream；消费者没提交 offset，恢复后从上次位置继续。systemd watchdog 仍然保留，作为「进程活着但服务不可用」的兜底（见 11.3）。

**面试点**：这是「故障时快速失败」和「依赖客户端自愈」两种立场的取舍，取决于客户端库是否有可靠的重连能力。

### 2.3 一个容易忽略的正确性细节

relay 使用**独立的 Kafka Writer**（`main.go` 中的 `persistWriter`）。

RabbitMQ 版本里这是**正确性要求**：publisher confirm 按 AMQP channel 顺序送达，如果朋友圈/点赞和消息持久化共用一个 channel，relay 读到的 confirm 可能是前面某条点赞消息的确认，会造成「消息还没真正到达 RabbitMQ 就 XACK 删除了 Stream 事件」的数据丢失。

Kafka 版本里 `WriteMessages` 是同步调用，返回值只对应本次写入的消息（`RequiredAcks=all`，所有 ISR 副本确认），不存在 confirm 错配的问题。保留独立 Writer 是出于**隔离性**：Writer 内部按 Topic/分区攒批，共用时点赞高峰会拉长持久化事件的写入延迟，而这个延迟直接决定 `serverAck` 的返回时间。

## 3. 核心链路一：私聊消息全链路

承接 1.2 的架构主张，这一节把完整调用链逐步拆开。

### 3.1 全景时序

```
发送方 A                    GoIM Server                      Kafka/Redis                接收方 B
  │                             │                              │                          │
  │─ WS {type:"msg"} ──────────▶│                              │                          │
  │                             │ ① JSON 解码 + 字段校验        │                          │
  │                             │ ② Redis Lua 原子执行 ────────▶│                          │
  │                             │    · 好友校验(双向)           │                          │
  │                             │    · 黑名单校验               │                          │
  │                             │    · clientMsgId 去重         │                          │
  │                             │    · 分配 serverMsgId         │                          │
  │                             │    · 写 inbox_order/data      │                          │
  │                             │    · 写 conv_order/meta       │                          │
  │                             │    · HINCRBY unread           │                          │
  │                             │    · XADD 持久化事件          │                          │
  │                             │◀──────────────────────────────│                          │
  │        （此时消息已可被同步读取，但还没落库、也还没推送）      │                          │
  │                             │ ③ relay 读 Stream ───────────▶│                          │
  │                             │ ④ WriteMessages(acks=all) ──▶│                          │
  │                             │◀── ISR 全部确认 ─────────────│                          │
  │                             │ ⑤ XACK + XDEL                │                          │
  │◀─ WS {serverAck} ───────────│ ⑥ 推送 serverAck / 转发 msg ─────────────────────────▶│
  │                             │                              │                          │
  │                             │ ⑦ 消费者落 MySQL（幂等）      │                          │
```

**关键：`serverAck` 和给 B 的推送发生在 ④ 写入确认成功之后，而不是 Lua 成功之后。** 这是 BUG-007 的修复结果（`backend/docs/问题反馈记录.md:20`）：早期版本在 Lua 成功后立即 ACK，客户端收到 ACK 立刻撤回/删除时会因为消费者还没写 Redis 而失败。现在把 ACK 后移到「消息已可靠交给 MQ」这个点，**保证「收到 ACK ⇒ 消息可撤回 / 可删除 / 可同步」这个不变量成立**。

### 3.2 各步骤的代码坐标

| 步骤 | 代码位置 | 说明 |
| --- | --- | --- |
| ① 解码 + 校验 | `service/msg_service.go:69-91` | `ClientMsgID` 非空且 ≤128、`ToID>0`、`MsgType>0`、`Content ≤ 1MB` |
| ② Lua 原子写 | `redis/lua_message_write.go:39-103`（脚本）、`:183-199`（Go 调用） | 见下文逐行解析 |
| ③ relay 读 Stream | `relay/message_relay.go:59-97` (`run`) | 先 `XAUTOCLAIM` 接管 pending，再 `XREADGROUP` |
| ④ 发布 + 写入确认 | `repository/mq_repo.go`（`PublishPersistEvent` → `publish`） | 同步 `WriteMessages`，`RequiredAcks=all`，会话 ID 作分区 Key，5s 超时 |
| ⑤ XACK+XDEL | `repository/message_pipeline.go:144-154` | pipeline 内同时写确认标记 |
| ⑥ 推送 | `relay/message_relay.go:172-190` (`pushAfterConfirm`) | 给 A 发 `serverAck`，给 B 发 `msg` |
| ⑦ 落库 | `consumer/message_persist_consumer.go`（`handle`） | 只有这一步，职责极窄；失败转投 retry Topic |

### 3.3 Lua 脚本逐段解析（`luaPrivateMsgWrite`）

这是全项目最核心的 60 行，面试时能讲透它就是加分项。

```lua
-- ① 会话 ID：双方算出同一个值（小的在前）
local convID = 'p_' .. math.min(sender, receiver) .. '_' .. math.max(sender, receiver)

-- ② 好友关系双向校验：两个 key 都必须存在
if redis.call('EXISTS', KEYS[1]) == 0 or redis.call('EXISTS', KEYS[2]) == 0 then
  return {1,0,0,0,0,'',0}   -- MsgWriteNotFriend
end
-- ③ 黑名单
if redis.call('SISMEMBER', KEYS[3], sender) == 1 then
  return {2,0,0,0,0,'',0}   -- MsgWriteBlocked
end

-- ④ 去重：key 形如 msg_dedup:{senderId}:{clientMsgId}，命中则返回原消息 ID
local old = redis.call('GET', KEYS[4])
if old then ... return {5, data.id, ...} end   -- Duplicate

-- ⑤ 服务端时间 + 消息 ID
local t = redis.call('TIME')
local ts = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)   -- 毫秒
local seq = redis.call('INCR', 'msg_id_seq:' .. ts)                     -- 同毫秒内序号
if seq == 1 then redis.call('EXPIRE', seqKey, 2) end
if seq > 999 then return redis.error_reply('message ID sequence overflow') end
local msgID = ts * 1000 + seq                                          -- 毫秒*1000+序号

-- ⑥ 写读模型：order ZSet + data Hash 分离
ZADD inbox_order:{sender}   ts msgID ;  HSET inbox_data:{sender}   msgID senderJSON
ZADD inbox_order:{receiver} ts msgID ;  HSET inbox_data:{receiver} msgID msgJSON
-- 同时写旧结构 inbox:{uid}（ZSet member = 完整 JSON）以兼容回退

-- ⑦ 会话列表
ZADD conv_order:{uid} ts convID ; HSET conv_meta:{uid} convID summary   （双方）
-- ⑧ 未读
HINCRBY unread:{receiver} convID 1

-- ⑨ 追加持久化事件到 Stream
local eventID = redis.call('XADD', KEYS[5], '*', 'payload', event, ...)
return {0, msgID, ts, 0, isOnline, eventID, 0}
```

**五个必须能讲的设计点**：

1. **消息 ID 为什么是「毫秒 × 1000 + 序号」而不是 `INCR msg_id_global`？**
   BUG-004（`问题反馈记录.md:17`）：全局计数器**一旦重置就会与 MySQL 已有主键冲突**（Redis 没持久化时重启，`INCR` 从 1 重新开始，而 MySQL 里 id=1 已存在 → 主键冲突 → 消费者反复 nack → 无限重复推送）。
   改成「时间成分 + 同毫秒序号」后，ID **单调递增且不依赖任何持久化状态**，重启也不会重号。序号 key 带 2 秒 TTL 自动回收，单毫秒上限 999 条消息（超过直接报错，是明确的容量边界）。
   *副作用*：ID 是 16 位数字量级（当前约 `1.78e15`），**超过了 JavaScript `Number.MAX_SAFE_INTEGER`（9.007e15）的安全边界吗？** 没有——1.78e15 < 9.007e15，安全。但代码里对此非常小心：`lua_message_write.go:64,78-79` 用 `string.format('%.0f', msgID)` 强制不用科学计数法，INT-039（`docs/前后端联调问题记录.md:82`）就是 cjson 把大整数编码成科学计数法导致反序列化失败的教训。**面试时这是个非常好的「浮点精度 / JS 安全整数」考点。**

2. **为什么校验、去重、ID 分配、状态写入必须在一个 Lua 里？**
   分步执行会有竞态窗口：步骤间好友关系可能被删除 → 消息发给非好友。Lua 在 Redis 单线程内原子执行，**要么全部通过，要么全部拒绝**。且把 5 次网络往返压成 1 次 `EVALSHA`。

3. **为什么同时写新结构（`inbox_order` + `inbox_data`）和旧结构（`inbox`）？**
   灰度迁移期的**双写兼容**：新代码读新结构（`redis_repo.go:139-141` 优先判断 `inbox_order:{uid}` 是否存在），旧代码/回退版本读旧结构。这是「不停机迁移」的标准做法。

4. **`inbox_order`（ZSet: msgID→timestamp）+ `inbox_data`（Hash: msgID→JSON）分离的价值**：
   旧结构把**完整 JSON 当 ZSet member**，导致「更新一条消息（撤回/已读）必须扫描整个 ZSet 逐个反序列化比对」。分离后，按 msgID `HGET`/`HSET` 直接定位——这是 `backend/docs/消息链路改造设计.md:92-108` 明确提出的改造，也修掉了 INT-021（「Redis 以完整 JSON 为成员导致同一 convId 重复」，`前后端联调问题记录.md:64`）。

5. **发送者也写一份 inbox（`readStatus=1`）**：
   让**发送方的离线同步走同一条路径**——不需要为『我发的消息』单独设计同步逻辑。代价是存储翻倍，但换来逻辑统一。

### 3.4 为什么私聊是「推模型」

- 每个用户**只有一个** `inbox`，消息只写 1 份（接收者）+ 1 份（自己）。
- 接收方上线只需读自己的 inbox，**不需要遍历任何东西**。
- 未读状态天然嵌在消息里（`readStatus`）。

对比群聊的拉模型（下节），这个「推拉结合」是 IM 领域标准解法。

## 4. 核心链路二：群聊消息与未读水位线

### 4.1 群聊与私聊的三处关键差异

| 维度 | 私聊 | 群聊 |
| --- | --- | --- |
| 存储 | 每用户 1 个 `inbox` | 每群 1 个 `outbox`（**成员共享**） |
| 消息副本数 | 2（双方各 1） | **1**（全群共享） |
| 未读 | `HINCRBY unread:{uid} convID` | **水位线计算**（不再逐成员写） |
| 额外序列 | 无 | `INCR group_seq:{gid}` 群内递增序号 |

**「500 人群只存 1 份 vs 推模式存 500 份」是必答的数字对比**（`backend/docs/产品技术设计.md:1857-1866` 有完整论述）。代价是离线同步要遍历用户所在的所有群，但用户平均只有 5–10 个群，开销可忽略。

### 4.2 群聊 Lua 的独特之处（`luaGroupMsgWrite`）

```lua
-- ① 成员校验：不在集合里直接拒绝（这是发送鉴权的核心）
if redis.call('SISMEMBER', KEYS[1], sender) == 0 then return {3,...} end
-- ② 禁言校验：从 group_member_info Hash 读 muted
local memberInfo = redis.call('HGET', KEYS[2], sender)
if info.muted then return {4,...} end
-- ③ 群序号
local groupSeq = redis.call('INCR', KEYS[4])      -- group_seq:{gid}
-- ④ 只写 1 份到 outbox
ZADD outbox_order:{gid} ts msgID ; HSET outbox_data:{gid} msgID msgJSON
-- ⑤ 遍历成员，只为更新会话列表（不再写未读！）
for _, uid in ipairs(members) do
  ZADD conv_order:{uid} ts convID ; HSET conv_meta:{uid} convID summary
end
```

**注意 ⑤ 的注释**（`lua_message_write.go:155-156`）：

> 群未读采用水位线模型（未读 = 群最新 seq − 成员已读游标，读取端计算），因此这里不再对每个成员 HINCRBY unread。

### 4.3 未读水位线改造（一个完整的「性能 + 语义」双修案例）

**改造前的问题**（`backend/docs/群聊未读水位线改造方案.md:17-27`）：

1. **语义粗糙**：`readAck` 只会把整个会话未读**清零**，服务端不知道用户「读到第几条」。中途来新消息时无法精确表达。
2. **写放大 O(N)**：每条群消息给每个成员写一次未读——500 人群每条消息 500 次 `HINCRBY`。
3. **半实现**：`group_read_pos` 在 repository 层已实现却从未接入。

**改造后**：

```
读模型：
  group_seq:{gid}                     ← 群最新序号（发送时 INCR）
  group_read_pos:{uid}  Hash          ← convID → 我已读到的 seq（readAck 时写）

未读 = max(0, GET group_seq:{gid} − HGET group_read_pos:{uid} g_{gid})
```

- 发送路径：**移除**逐成员 `HINCRBY`，每条群消息每成员的写次数从 3 降到 2。
- 已读路径：`readAck` 携带 `lastReadGroupSeq`，**写游标而非清零**。
- 读取路径：`GetUnreadMap` 对 `g_` 前缀**改为游标差计算**（`repository/redis_repo.go:338-406`）。

**协议兼容设计（重点）**：`readAck` 的 `lastReadGroupSeq` 是**可选字段**（`model/message.go:81-86`）：

```go
type ReadAck struct {
	ConvID string `json:"convId"`
	// 缺省(0)时服务端降级为"标记到当前最新"（等价旧的整会话清零）；私聊忽略此字段。
	LastReadGroupSeq int64 `json:"lastReadGroupSeq,omitempty"`
}
```

服务端降级逻辑在 `service/msg_service.go:297-331`：seq ≤ 0 时读当前 `group_seq` 作为游标 → **老客户端行为完全不变**。这是很好的「协议演进 + 向后兼容」范例。

**迁移的数学正确性（非常值得讲）**：`scripts/migrations/012_group_read_pos_init.lua` 需要在**旧代码仍在运行**时执行：

```
迁移时：      read_pos_init = seq₁ − unread₁
迁移后发布前：旧 Lua 继续 HINCRBY，unread 增长 N 条
发布后：      未读 = seq₂ − read_pos_init
                  = (seq₁ + N) − (seq₁ − unread₁)
                  = unread₁ + N   ← 恰好等于当时的 hash 值 ✓
```

**先迁移、后发布**的顺序在数学上保证徽标连续，不丢不错。`repository/redis_repo_integration_test.go:104-133` 用真实 Redis 验证了这个不变量。

**新成员入群**：游标初始化为当前 seq（`redis_repo.go:491-500`），所以**历史消息不计入未读**——符合产品直觉（刚进群不该看到 500 条未读）。

**防御性设计**：游标缺失时视为「已读到最新」（`redis_repo.go:390-393`），避免水位线计算出巨大的未读数导致徽标爆炸。

### 4.4 群聊推送：relay 里的 fanout

`relay/message_relay.go:177-189`：写入确认成功后遍历 `evt.Recipients` 推送（跳过发送者）。`Recipients` 来自 Lua 返回的**成员快照**（发送那一刻的成员集合），不是「推送时再查成员」—— 这样**成员在发送与推送之间被移除，仍会收到那一条消息**，但与「消息确实写入 outbox 时他在群里」的事实一致，语义是合理的。

## 5. 可靠性与一致性设计

这是后端面试最能拉开差距的部分。项目在这块做得比一般个人项目深。

### 5.1 「三种成功」的清晰区分

`backend/docs/消息链路改造设计.md:43-47` 明确提出三个不同层次的「成功」，这个思维模型本身就是加分项：

| 层次 | 含义 | 客户端可观察到 |
| --- | --- | --- |
| Lua 成功 | 消息进入 Redis 读模型 | 可被 `syncReq` 同步到 |
| **MQ 写入确认成功** | 持久化事件已可靠交给 MQ（Kafka ISR 全部确认） | **收到 `serverAck` + 实时推送** |
| MySQL 落库成功 | 长期归档完成 | 可被 `/msg/search` 检索 |

关键设计：**只在第 2 层给客户端 ACK**，而不是第 1 层。理由见 3.1。

### 5.2 集群内故障处理矩阵

`backend/docs/消息链路改造设计.md:194-202` 的表格，逐条都能在代码里找到对应实现：

| 故障 | 预期行为 | 代码证据 |

### 5.3 幂等：从「客户端去重」到「服务端幂等」的三层防护

**第 1 层：客户端 `clientMsgId`（短窗口去重）**
- 前端用 `crypto.randomUUID()` 生成（`stores/chatStore.ts:150`）。
- 重试时**复用同一个 `outbound` 帧**（`chatStore.ts:34,179`）——这是幂等能生效的前提。
- Lua 内 `GET msg_dedup:{sender}:{clientMsgId}` 判重，TTL 300 秒（`lua_message_write.go:50-55`）。
- **窗口只有 5 分钟**，所以**不能**把它当作长期唯一键（`消息链路改造设计.md:166` 明确说明）。

**第 2 层：服务端 `serverMsgId` 作为 MySQL 主键（永久幂等）**
`repository/mysql_repo.go:87-89` 的写法很讲究：

```sql
INSERT INTO private_messages (id, client_msg_id, ...) VALUES (...)
ON DUPLICATE KEY UPDATE id = id          -- 命中重复时什么都不改
```

然后 `:102-115` 检查 `RowsAffected() == 0`（说明是重复）→ **回查并逐字段比对**：

```go
if stored.ClientMsgID != msg.ClientMsgID || stored.SenderID != msg.SenderID || ... {
    return fmt.Errorf("private message id %d conflicts with existing content", msg.ID)
}
```

**为什么要比对内容？** 因为这能区分两种情况：
- **重放**（内容一致）→ 视为成功，ACK；
- **ID 碰撞**（内容不一致）→ 报错进死信，**绝不覆盖已有消息**。

这比简单的 `INSERT IGNORE` 严格得多，是有数据安全意识的写法。

**第 3 层：MQ 消费者手动提交 offset**
所有消费者都走 `consumer/kafka_runner.go` 的 `runReader`：`FetchMessage` → 处理 → 成功后同步 `CommitMessages`（Reader 配置 `CommitInterval=0`，不自动提交），**处理成功才推进 offset**。处理失败时在分区内指数退避重试（200ms 到 10s）；handler 返回 `drop(err)` 表示永久错误（如 JSON 损坏），记录日志后直接提交跳过。

### 5.4 MQ 重试与死信：用 retry Topic 实现延迟重试

Kafka 没有消息级 TTL 和死信交换器，也不能把单条消息「放回队尾」。如果在主 Topic 原地重试，一条落库失败的消息会**阻塞整个分区**。所以 `message_persist` 用了三个 Topic：

```
message_persist        ──落库失败──▶ message_persist_retry（header: x-retry-count, x-retry-at=now+5s）
       ▲                                   │ retry 消费者等到 x-retry-at 后写回主 Topic
       └───────────────────────────────────┘
x-retry-count ≥ 5 ──▶ message_persist_dlq
```

失败重试流程（`message_persist_consumer.go` 的 `retryOrDeadLetter` / `handleRetry`）：

1. 计数 `x-retry-count` < 5 → 写入 `message_persist_retry`，**写成功后**主 Topic 才提交 offset；写失败则返回 error，由 runReader 原地退避，保证不丢；
2. retry 消费者读到消息，sleep 到 `x-retry-at` → 写回主 Topic；
3. 达到 5 次 → 写入 DLQ 并提交 offset。

**为什么 retry 消费者可以 sleep？** retry Topic 里的消息延迟相同（都是 5s），并且按写入顺序排列，所以队头消息等待时，后面的消息一定还没到期，不会被拖慢。

**为什么需要延迟？** 避免「1 秒内耗尽重试次数」：MySQL 重启 3 秒，如果立刻重投，5 次重试在毫秒内烧完，所有消息都会进死信。

**对比 RabbitMQ 版本**：原来用 `message_persist_delay` 队列 + `x-message-ttl=5000` + DLX 回流主队列，同样不依赖延迟插件。Kafka 版本把「TTL 到期」换成「消费者读 header 判断到期」，思路一致。

**注意 legacy 消费者只做分区内退避重试**（`private_msg_consumer.go`、`group_msg_consumer.go`），没有 retry Topic——因为它们是回退路径，且会重复推送（这正是新架构要解决的问题之一）。

### 5.5 Redis Stream relay 的失败待办机制

这是项目里**最有深度的可靠性设计**，值得完整讲。

**问题**：Stream 消息投递失败时如果不 ACK，会一直留在 Pending Entries List；如果 Kafka 长时间故障，Stream 会**无限堆积**。

**方案**（`relay/message_relay.go:21-31,99-170`）：

```
投递失败
  ├─ 事件年龄 < 30 分钟 → 保留在 Stream pending，等 10s 后的 XAUTOCLAIM 重试
  └─ 事件年龄 ≥ 30 分钟 → moveToBacklog: 先 LPUSH 到 relay_failed_events
                          → 再 XACK+XDEL 从 Stream 摘除
```

**关键的顺序保证**（注释 `relay.go:130-132`）：

> 先写待办、再摘除 Stream 条目。若两步之间崩溃，事件会同时存在于待办与 Stream（重复投递由 MySQL 幂等消化），但**绝不会出现"已摘除却无处保存"的丢失窗口**。

这是经典的 **at-least-once 优先于 at-most-once** 的取舍——**允许重复，绝不允许丢失**。

**待办重放**：每轮循环调用 `replayBacklog`（`relay.go:142-170`），投递成功才 `LREM` 移除；失败保留等下轮。待办长度超 1000 触发 error 级告警，提示系统处于降级状态。

**XAUTOCLAIM 的必要性**（`relay.go:68`）：relay 用 Consumer Group 消费，若某个 consumer 崩溃，它的 pending 消息会永远卡住。`XAUTOCLAIM`（minIdle=10s）接管超时未处理的消息——**这正是 Redis Stream 相比 List 的核心优势**。

**为什么不用未确认消息 TTL？**（`消息链路改造设计.md:134-143`）Redis Stream 没有安全的**单条**消息 TTL；对整个 Stream 设 TTL，可能在 Kafka 故障时**删掉还没发送的事件**。所以采用「确认后立即 XACK+XDEL + 定时清理残留」的策略。

**兜底清理**：`infra/cleanup.go:194-216` 的 `cleanupConfirmedPersistEvents` 是**标记驱动**的——只有 `message_persist_confirmed` 集合里存在记录才删除，**绝不按年龄单独裁剪**，因此停机不会误删未确认事件。

| 数据 | 一致性策略 | 理由 |
| --- | --- | --- |
| 消息内容 | Redis 先行 + MQ 异步落库（最终一致） | 可容忍 <1s 窗口 |
| **好友关系** | MySQL 为准 + Redis 缓存（`friend:{a}:{b}`） | 发送鉴权依赖，必须准 |

### 5.7 群成员移除的顺序设计（一个细节亮点）

`service/group_service.go:239-247`（移除）：

```go
// Remove Redis authorization first. Once this returns, a removed user can
// no longer pass the send-time Lua membership check, even if the following
// MySQL write is temporarily unavailable.
if err := s.redisRepo.RemoveGroupMemberRedis(...); err != nil { return err }
if err := s.mysqlRepo.RemoveGroupMember(...); err != nil { return err }
```

**为什么先删 Redis？** 因为**发送鉴权读的是 Redis**（`SISMEMBER group_members:{gid}`）。先删 Redis ⇒ 被移除者**立即**无法发消息；即使 MySQL 写失败，后果是「MySQL 里还有一条记录但发不了消息」——**比「MySQL 已删但还能发消息」安全得多**（后者是越权）。

**反向操作（新增成员）顺序相反**（`group_service.go:183-193`）：

```go
if err := s.mysqlRepo.AddGroupMember(...); err != nil { return err }
if err := s.redisRepo.AddGroupMemberRedis(...); err != nil {
    // Returning success here would leave the send-time Lua authorization
    // cache stale. The caller must retry/repair instead of believing the
    // member can already send messages.
    return fmt.Errorf("sync group membership to redis: %w", err)
}
```

先写 MySQL（权威），再写 Redis；**Redis 失败必须让整个请求失败**，不能只记日志返回成功——否则用户以为加进去了，实际发不了消息。

**这对「先写哪个」的不对称处理，取决于「失败时哪种状态更危险」**，是很好的面试展开点。

**群成员缓存的自我修复**（`service/msg_service.go:175-188`）：滚动发布/Redis 冷启动时，Lua 报 `MsgWriteNotMember` → Go 层从 MySQL 加载成员集合 `WarmGroupMembers` 回填 → **重试一次 Lua**。这是 `NewMsgServiceWithMySQL` 存在的唯一理由（`msg_service.go:52-60`）。

### 5.8 事务的缺失（诚实的自我批评）

**项目几乎不使用 MySQL 事务**。`CreateFriendship` 插入双向记录是**两条独立 INSERT**（`mysql_repo.go:313-325`）：

```go
_, err = m.db.ExecContext(ctx, query, fs.UserID, fs.FriendID)
_, err = m.db.ExecContext(ctx, query, fs.FriendID, fs.UserID)
```

如果第二条失败，会留下**单向好友关系**。同理 `AcceptFriendRequest`（`friend_service.go:148-172`）里的「更新申请状态 → 建好友关系 → 写缓存 → 建会话 → 回填动态」是 5 个独立操作，中途失败会留下不一致。

**面试时的正确答法**：「这是已知的不足。`uk_bidirectional` 唯一约束能防重复，但防不了半成功。改进方向是在 repository 层用 `BeginTx` 把双写包起来，或者至少在 `CreateFriendship` 内部用事务。当前没有事务是因为依赖 MySQL 的原子单语句 + 幂等重试，但这在『两条 INSERT』这种场景下不成立。」

### 6.3 撤回脚本的细节（`luaRevokeMsg`）

**私聊撤回必须同时改双方副本**（`lua_revoke_msg.go:60-84`）：

> A private message is stored in both participants' inboxes. Updating only the sender's copy makes the receiver see the old content after a refresh.

所以脚本**先找到并校验两份副本**（都必须是 sender 发的、都在 2 分钟窗口内），再用一次 Lua 调用原子替换。

**保持原 timestamp 不变**（`lua_revoke_msg.go:35-37` 注释）：

> The timestamp is also the sync cursor, so changing it would make the same message appear again as a new message after a client reconnects.

**这是很细的洞察**：同步游标就是 timestamp，如果撤回时改了它，客户端重连后会把同一条消息当成新消息再收一次。

**2 分钟窗口**：`nowTimestamp - original.timestamp > 120000 → return 0`（`:53,69`）。

**权限校验**：`original.fromId ~= tonumber(userID) → return 0`（`:50,66`）—— 只有发送者能撤回。

### 6.4 点赞的原子性与缓存击穿防护

**点赞 Lua**（`lua_moment_like.go:22-29`）：

```lua
local added = redis.call('SADD', KEYS[1], ARGV[1])
if added == 1 then return {1, redis.call('INCR', KEYS[2])} end   -- 新增赞
return {0, tonumber(redis.call('GET', KEYS[2]) or '0')}          -- 重复赞：幂等
```

**天然幂等**：判重与计数在同一原子操作内，重复点赞不会重复计数。

**缓存预热防击穿**（`repository/redis_repo.go:836-888`）——这里有一个完整的三层防护：

1. **先查 `moment:like_loaded:{mid}` 标记**，已预热直接返回；
2. **未预热则抢 `moment:like_lock:{mid}`（SETNX, 5s）**，只有一个请求回源 MySQL；
3. 抢不到锁的请求**轮询 loaded 标记 ~200ms**（20 次 × 10ms），仍未就绪则「尽力而为」返回（TTL 兜底，下次再预热）；
4. 抢到锁后**二次确认**（可能在抢锁间隙被别人预热完）；
5. 回源后 pipeline 写入：`DEL set` → `SADD` → `EXPIRE` → `SET count` → `SET loaded`。

**为什么必须有「预热」这一步？** 因为如果直接对冷 key 做 `SADD`+`INCR`，会把 MySQL 里的历史点赞**当成 0**，导致老用户的赞被误判为「新赞」而重复计数。`EnsureMomentLikesLoaded` 保证在**任何点赞/读取前**集合与计数已与 MySQL 一致。

**批量削峰落库**（`consumer/like_persist_consumer.go:81-174`）：
- 攒批：`batchSize=200` 或 `flushMs=500` 触发 flush；
- **按 `(momentID, userID)` 折叠，last-action-wins**（map 覆盖天然实现）；
- 分成一批 `INSERT IGNORE` + 一批 `DELETE`，各一条 SQL；
- 整批成功后一次性 `CommitMessages` 提交该批 offset；失败整批退避重试，不提交（fetch 与 batch 拆成两个 goroutine，通过 channel 衔接）。

**收益**：1000 次点赞从 1000 条 SQL 降到约 2 条，且 `INSERT IGNORE` 依赖唯一键 `uk_moment_user` 保证重投安全（`mysql_repo.go:655-673`）。

### 6.5 清理任务

`infra/cleanup.go` 后台 goroutine，启动时立即跑一次，之后每小时一次（`main.go:222`）：

- **时间阈值**：删 3 天前的条目（`cleanupAgeDays = 3`）；**注意 BUG-002**：阈值必须是 `UnixMilli()` 而非 `Unix()`（`cleanup.go:78`），因为 ZSet score 用毫秒。
- **数量上限**：inbox 1000、outbox 500、timeline 100、conv_list 不限量（`maxEntriesForPrefix`）。
- **索引配对删除**：`inbox_order` 与 `inbox_data` 必须**同时删**，否则 Hash 泄漏（`cleanKey`/`cleanIndexedOrder` 用 pipeline 保证）。
- **Stream 兜底**：只删已确认的（见 5.5）。

## 7. 其余业务链路

### 7.1 好友关系

**表设计**（`scripts/migrations/002_create_friendships.sql`）：

```sql
friend_requests:  UNIQUE KEY uk_pair (from_user_id, to_user_id)
friendships:      UNIQUE KEY uk_bidirectional (user_id, friend_id)
```

**friendships 存双向两行**（`CreateFriendship` 插两条），查询「我的好友」只需 `WHERE user_id = ?`，无需 `OR`——**读优化，写放大 2 倍**。

**好友申请的状态机**：`0=待处理 → 1=已接受 / 2=已拒绝`。

**BUG-008 的 upsert 技巧**（`mysql_repo.go:239-246`）值得单独讲——唯一约束 `uk_pair` 会导致「被拒绝后重新申请」冲突，解法是把 INSERT 改成带条件的 upsert：

```sql
INSERT INTO friend_requests (from_user_id, to_user_id, message, status) VALUES (?,?,?,?)
ON DUPLICATE KEY UPDATE
    id = LAST_INSERT_ID(id),                              -- 让 LastInsertId 返回已有 id
    message    = IF(status = 0, message,    VALUES(message)),
    created_at = IF(status = 0, created_at, NOW()),
    updated_at = IF(status = 0, updated_at, NOW()),
    status     = IF(status = 0, status,     VALUES(status))
```

- **待处理时（status=0）**：所有字段保持原值 → 幂等，不覆盖；
- **已处理时**：重置为新的 `status=0` 并更新时间留言 → 复用原 ID 重新申请。

`LAST_INSERT_ID(id)` 是 MySQL 的一个巧妙技巧：upsert 命中时让 `LastInsertId()` 返回**已存在行的 id**，这样 Go 层拿到的 `req.ID` 始终有效。

**接受好友的连带效应**（`service/friend_service.go:163-185`）：
1. 写 Redis 好友缓存（**Lua 发送鉴权的依赖**）；
2. 为双方各建一个**空会话摘要**（让好友出现在会话列表，即使还没聊过）—— 这是 INT-019 的衍生需求；
3. **回填对方最近 1000 条历史朋友圈**（`backfillFriendMoments`，跳过 `visibility=3`）—— 因为 Feed 是发布时扇出的，新好友看不到之前的内容。

**删除好友**（`friend_service.go:362-380`）：删 MySQL 双向 → 删 Redis 缓存。缓存删除失败**只记日志**，因为「MySQL 是真相源，删了缓存下次会重建」；但不删缓存会导致**已删好友仍能发消息**，所以这里其实有个小风险窗口。

### 7.3 朋友圈 Feed：推拉结合（Push-Pull Hybrid）

这是除消息外第二个有深度的设计。

**问题**：纯写扩散（fan-out on write）在「大V」场景下会爆炸——100 万粉丝的用户发一条动态要写 100 万次 ZSet。

**方案**（`service/moment_service.go:468-602`）：按作者好友数分流。

```
发布时（consumer/moment_feed_consumer.go:105-167）：
  1. 总是写作者自己的寄件箱 moment_outbox:{author}
  2. visibility == 3（仅自己）→ 到此为止，不扩散
  3. CountFriends(author) > big_user_friend_threshold(默认 500)
       → 标记 moment:big_users（sticky），跳过写扩散
  4. 否则 → pipeline 写扩散到所有好友的 timeline:{friend}，并裁剪到 timelineMaxLen

读取时（moment_service.go:488-517）：
  源 1：自己的寄件箱（自见）
  源 2：自己的收件箱（普通好友推来的）
  源 3：所有「大V好友」的寄件箱（拉取）
  → 各源取一页 limit+1 → 按 momentID 去重 → 按 (ts desc, id desc) 归并 → 取 limit
  → nextCursor = base64("{ts}_{id}")   复合游标
```

**为什么用复合游标 `(ts, id)` 而不是纯时间戳？**
同一毫秒可能有多条动态。只用 ts 分页会在边界重复或漏读。`getFeedPage`（`redis_repo.go:754-783`）分两段读：
- 第一段：`ts == maxTs` 且 `id < maxID`（同毫秒内继续翻）；
- 第二段：`ts < maxTs`（开区间 `(maxTs`）。

**「大V集合是 sticky 的」**（`MarkBigUser` 只增不删，`redis_repo.go:709-715`）——一旦成为大V就永久走拉模式。这避免了「好友数在阈值附近波动导致扩散策略反复切换」的不稳定状态。

**MQ 失败时的同步补偿**（`moment_service.go:84-94`）：发布动态时若 `PublishMomentPush` 失败，**同步执行 `distributeMomentFallback`**（写寄件箱 + 直接扇出好友），避免「发布成功但谁都看不到」。这是 INT-034 的修复（`前后端联调问题记录.md:77`）。

**游标是 base64 的不透明字符串**（`moment_service.go:608-611`）：`encodeCursor` 用 `base64.RawURLEncoding`，好处是客户端无法依赖内部结构，服务端可自由改进分页实现。

### 7.4 消息搜索：

- MySQL 表有 `FULLTEXT INDEX ft_content (content)`（`004_create_messages.sql:10,23`）；
- 但 `SearchPrivateMessages`（`mysql_repo.go:804-828`）实际用的是 **`LIKE '%query%'`**，**没有走全文索引**。

**这是一个可以主动说的优化点**：`LIKE '%...%'` 前导通配符无法使用 B-Tree 索引，而 `FULLTEXT` 索引存在却未被使用。改进方向是改用 `MATCH(content) AGAINST(? IN BOOLEAN MODE)`，或引入 ngram parser 支持中文分词。

### 8.2 WebSocket 连接生命周期

**握手**（`ws/upgrade.go:32-104`）：

```
1. c.Query("token") → 缺失返回 401
2. middleware.ParseToken 校验 → 失败返回 401
3. upgrader.Upgrade（CheckOrigin 返回 true，允许所有来源）
4. conn.NewClientConnection(claims.UserID, wsConn)
5. cm.KickOld(userID, client)         ← 单设备策略
6. Redis: SET online:{uid} "1" EX 60 ; SET conn:{uid} "ws:{nano}" EX 60
7. 启动 goroutine：每 20s 续期 online/conn（TTL 60s）
8. go client.WritePump() ; go client.ReadPump(handler)
```

**`CheckOrigin` 无条件返回 true**（`upgrade.go:22`）是一个安全缺口：**任何网站都能用受害者的 token 建立 WS 连接**（如果 token 泄露）。生产应校验 Origin 白名单。

**双 goroutine 模型**（`conn/client.go`）：

| 常量 | 值 | 位置 |
| --- | --- | --- |
| `maxMessageSize` | 4096 字节 | `:11` |
| `writeWait` | 10s | `:12` |
| `pongWait` | 60s | `:13` |
| `pingPeriod` | 30s（必须 < pongWait） | `:14` |
| `SendCh` 容量 | 256 | `:32` |
| `KickCh` 容量 | 1 | `:33` |

**ReadPump**（`:42-77`）：设 read limit + deadline，注册 Pong/Ping handler 续期 deadline，循环 `ReadMessage` → 回调。退出时关闭 `Conn` 和 `CloseCh`。

**WritePump**（`:83-120`）：`select` 四路——`KickCh` / `SendCh` / ping ticker / `CloseCh`。

> **BUG-001 的关键修复**（`问题反馈记录.md:14`）：kick 原先是「写 SendCh 后立即关 CloseCh」，`select` 会随机优先处理关闭分支，导致客户端有时收不到 kick 通知（只看到 1005）。修法是**专用 `KickCh`**，写协程按「先写 kick 消息 → 再发关闭帧」串行处理（`client.go:92-100`）。
> 这是一个非常典型的 **Go `select` 多路就绪随机选择** 导致的时序 Bug，面试时讲这个很有说服力。

**连接管理器**（`conn/manager.go`）：`sync.Map`，key 是 `userID`。

```go
type ConnectionManager struct {
	connections sync.Map // userID (int64) -> *ClientConnection
}
```

**⚠️ 这意味着每用户只能有一个连接**——单设备策略的代价：**同一浏览器开两个标签页会互相踢下线**，这也是前端联调中的已知现象。

**`KickOld`**（`:43-54`）：取旧连接 → 非阻塞发 `{"type":"kick","reason":"new_login"}` 到 `KickCh` → 从 map 删除 → 注册新连接。

```go
type SyncReq struct {
	LastSyncTime  int64 `json:"lastSyncTime"`
	LastSyncMsgID int64 `json:"lastSyncMsgId,omitempty"`  // 复合游标第二维
	BatchSize     int   `json:"batchSize"`
}
```

**为什么需要 `lastSyncMsgId`？** BUG-013（`问题反馈记录.md:26`）：同一毫秒有多条消息时，只用 `lastSyncTime` 做 `score >= lastSyncTime` 会导致**边界消息重复返回**，且「同时间戳消息较多时无法可靠推进」。

**修复**：
1. 协议升级为复合游标，响应增加 `syncMsgId`；
2. 仓储按 `(timestamp ASC, msgId ASC)` 严格向后读取（`redis_repo.go:178-191`）：
   ```go
   if m.Timestamp < lastSyncTime || (m.Timestamp == lastSyncTime && lastSyncMsgID > 0 && m.MsgID <= lastSyncMsgID) {
       continue
   }
   ```
3. `hasMore` 用「多取一条」判断（`msg_service.go:421`）；
4. 群已读位置**只推进到实际返回的消息**，不用它过滤历史（`:397-400` 注释：否则客户端清空本地状态后重新登录会永久缺消息——这是 INT-028）。

**同步流程**（`msg_service.go:367-467`）：

```
1. ReadInbox(userID, lastSyncTime, lastSyncMsgID, batchSize+1)     ← 私聊
2. GetGroupMemberships(userID) → 对每个群 ReadOutbox(...)           ← 群聊
3. 合并 privateMsgs + groupMsgs，按 (Timestamp, MsgID) 升序排序
4. hasMore = len > batchSize → 截断
5. syncTime/syncMsgID = 最后一条的 Timestamp/MsgID（空则用 now）
6. 推 syncBatch
7. 推 convSync（GetConvList + GetUnreadMap）
```

**注意第 2 步的容错**（`:390-394`）：`GetGroupMemberships` 失败时**只用私聊消息继续**，不整体失败。

**`convSync` 会覆盖前端本地未读**（`stores/chatStore.ts:235-249`）——服务端是未读的真相源。

### 8.5 前端契约的关键约定

**响应信封**（`api/response.go:17-21` + `frontend/docs/前端接口契约.md:9-11`）：

```json
成功：{ "code": 0, "message": "ok", "data": T }
失败：{ "code": 非0, "message": "..." }
分页：{ "items": T[], "pagination": { "total", "offset", "limit", "has_more" } }
```

**⚠️ 分页信封有例外**：
- `GET /group/list` 返回**裸数组** `Group[]`（`api/groups.ts:6`）；
- `GET /moment/feed` 返回 `{ moments, next_cursor }`（`api/moment_handler.go:81-84`），用的是 `moments` 而不是 `items`。

**三个不统一，是真实的技术债。**

**字段命名规律（重要，面试可能被问）**：
- **与数据库模型直连的实体用 snake_case**：`user_id`, `to_user_id`, `created_at`, `access_token`, `mute_list`；
- **与实时/运行态相关的用 camelCase**：`convId`, `msgId`, `fromId`, `toId`, `msgType`, `serverMsgId`, `lastReadGroupSeq`, `clientMsgId`。

**规律是**：HTTP 侧偏 snake_case（贴合 SQL），WS 侧全 camelCase（贴合 JS）。但 `MuteConversationRequest.convId` 和 `RevokeMessageRequest.msgId` 是 camelCase 混在 HTTP 里。**契约文档没有说明这条规律**——建议补上。

**时间格式的两种表示**：
- HTTP：`created_at`/`updated_at` 是 **RFC 3339 UTC 字符串**；
- WS：`timestamp`/`lastSyncTime`/`syncTime` 是 **Unix 毫秒**。

**ID 规则**：服务端资源 ID（含评论 ID）由 MySQL 自增生成，前端以 JSON `number` 接收并回传；**前端不得自行生成服务端资源 ID**；客户端消息去重 ID 用字符串 `msgId`。

**会话 ID 规则**（`model/common.go:28-36`）：

```go
私聊：p_{较小用户ID}_{较大用户ID}    // 排序保证双方算出同一个 ID
群聊：g_{群组ID}
```

**`readAck` 的群聊水位线**（8.2 已述，见第 4.3 节）。

### 8.6 前端 HTTP 客户端封装（后端需要知道的）

`frontend/src/api/client.ts` 的几个设计，理解它们有助于联调：

1. **`globalThis.fetch.bind(globalThis)`**（`:30`）：INT-007 的修复。原始 Bug 是把 `window.fetch` 存为实例字段后用 `this.fetchImpl()` 调用，浏览器抛 `Illegal invocation`，**所有 HTTP 请求全废**而后端日志静默无请求。**这是一个非常经典的 JS `this` 绑定陷阱**，面试时如果聊到联调排查可以讲。

2. **超时 15s + 双 AbortController 合并**（`:39-52`）：外部 `signal` 通过 `relayAbort` 转发进来，与内部超时共用。用 `controller.signal.aborted` 区分「超时」与「断网」。

3. **401 自动刷新 + 单次重试**（`:63-66`）：
   ```ts
   if (response.status === 401 && mayRetry && this.options.onUnauthorized) {
       const recovered = await this.options.onUnauthorized();
       if (recovered) return this.request<T>(path, init, false);   // mayRetry=false，只重试一次
   }
   ```

4. **两个 client 实例防递归**（`frontend/src/lib/api.ts:11-12,50-54`）：
   - `publicClient`（无 token、无 401 回调）用于 `login`/`register`/`refresh`；
   - `apiClient`（有 token、有 `onUnauthorized`）用于其余所有接口。
   **如果 `refresh` 也用带 `onUnauthorized` 的 client，刷新自身 401 会无限递归。**

5. **并发刷新去重**（`lib/api.ts:14-41`）：模块级 `refreshPromise` 单例。页面挂载时常有 3–4 个并发请求同时 401，单例把 N 次刷新合并成 1 次。`finally` 里的身份校验（`:38`）防止「A 的刷新未结束、B 又发起新一轮」时误清空。

### 8.7 前端状态管理分工（后端视角）

| 存储 | 技术 | 内容 | 持久化 |
| --- | --- | --- | --- |
| 服务端资源 | TanStack Query | 好友/申请/群/群成员/朋友圈/设置 | 内存，staleTime 30s |
| 会话身份 | Zustand `authStore` | token、过期时间、user | ✅ localStorage `goim-auth-v1` |
| 实时消息 | Zustand `chatStore` | 会话、消息 Map、连接状态、同步游标 | ❌ **不持久化** |

**`chatStore` 不持久化是 `syncReq` 存在的根本原因**：刷新 = 内存清空 = 每次都是「首次同步」（`lastSyncTime: 0`）。所以**服务端必须能处理 `lastSyncTime=0` 的全量拉取**。

**消息去重在前端是三层**（`stores/chatStore.ts`）：
1. `mergeServerMessages` 按 `serverMsgId` 去重 + 按 timestamp 排序（`:117-126`）；
2. `receiveMessage` 早退：`if (existing) return state`（`:206-207`）——**返回原引用，避免无谓重渲染**；
3. `acknowledge` 按 `clientMsgId` 匹配临时消息（`:192-194`）。

**`outbound` 字段保留原始发送帧**（`:34`）—— 保证重试时复用同一个 `msgId`，让服务端幂等生效。**这是前后端契约协同的关键点。**

**前端 WS 的已知限制**（后端需要知道以便设计补偿）：
- **无离线发送队列**：`readyState !== OPEN` 时 `send()` 返回 `false`，消息被标为 `failed`，靠用户手动重试（`realtime/socket.ts:47-51`、`chatStore.ts:168-170`）；
- **无心跳**（依赖服务端原生 Ping）；
- **重连无上限**：指数退避 `min(30s, 1s * 2^n)` + 0–350ms jitter（`socket.ts:90-99`）；
- **无多标签页协同**：无 `BroadcastChannel`、无 `storage` 事件监听 → token 刷新不跨标签页、且两标签页会互相踢下线。

## 9. 面试高频问答（按主题）

### 9.1 【架构】为什么消息要先写 Redis 而不是直接写 MySQL？

**四个理由**（`backend/docs/产品技术设计.md:1901-1920` 有完整论述）：

1. **性能**：Redis 写约 0.1ms，MySQL 写 5–10ms。高并发下「先写 MySQL 再推 Redis」会让响应延迟到 10ms+；Redis 先行把同步路径压到亚毫秒（实测 P50 0.23ms）。
2. **削峰**：热门群消息、朋友圈点赞高峰由 MQ 缓冲，MySQL 按自己的消费速率写入，避免高峰期打垮 DB。
3. **可靠性**：MQ 保证 at-least-once，即使 Redis 宕机，MQ 里的事件仍可落库。
4. **实时性**：消息一到 Redis 就能被对端同步拉取，不必等落库。

**代价**（必须主动说）：
- Redis 与 MySQL 有短暂不一致窗口（消费延迟，通常 <1s）；
- **Redis 从「纯缓存」升级为「消息状态存储」，必须开 AOF/副本、禁止危险淘汰**（`消息链路改造设计.md:15,118`）。当前部署的 `redis:7.2-alpine` 用的是默认 RDB 配置，**这是一个需要指出的风险**。

### 9.2 【架构】为什么私聊用推模式、群聊用拉模式？

```
私聊（推）：
  每用户 1 个 inbox ZSet，消息只写 1 份（+ 自己 1 份）
  接收方上线直接读自己的 inbox，无需遍历
  未读状态天然内嵌在消息里（readStatus）

群聊（拉）：
  每群 1 个 outbox ZSet，500 人共享同一份
  内存节省 499 倍（对比每人写一份）
  代价：离线同步要遍历用户所在的所有群
```

**关键数据**：用户平均 5–10 个群，遍历开销可忽略；而如果群聊用推模式，一条消息要写 500 份副本。**这是 IM 领域经典解法，微信也是类似方案。**

### 9.3 【并发】为什么用 Lua 而不是多条 Redis 命令？

发送前的校验链有 5 步：好友关系、黑名单、去重、ID 分配、状态写入。

**分步执行的问题**：
- 5 次网络往返；
- **竞态窗口**：Step 1 通过后、Step 2 执行前，好友关系可能被删除 → 消息发给了非好友。

**Lua 的价值**：Redis 单线程内原子执行，**要么全部通过、要么全部拒绝**；且只有 1 次 `EVALSHA` 往返。

**代价**：Lua 不可调试、无法复用其他命令、脚本过长会阻塞 Redis（Redis 有 `lua-time-limit`，超时后只记日志但**不会中断**）。当前项目最大的脚本是群聊写（含 500 人遍历），`消息链路改造设计.md:88` 明确留了压测 TODO。

### 9.4 【可靠性】怎么保证消息不丢、不重？

**不丢**（分层兜底）：
- 客户端：`clientMsgId` + 重试（`outbound` 保留原始帧）；
- 服务端：Redis Lua 成功 ⇒ 消息可同步；Kafka 持久化日志 + `acks=all` 写入确认（生产建议副本 3、`min.insync.replicas=2`）；
- relay：写入确认成功才 XACK+XDEL；写入超时**不删 Stream**（`relay.go:107-122`）；
- 消费者：手动提交 offset，落库成功才提交；失败转投 retry Topic 延迟 5s 重试最多 5 次 → DLQ；
- 降级：30 分钟超龄事件移入 `relay_failed_events` 待办，持续重放（**先写待办再摘 Stream**，不留丢失窗口）。

**不重**（幂等三层，见 5.3）：
- `clientMsgId` 5 分钟窗口去重；
- `serverMsgId` 作为 MySQL 主键 + 内容比对（`ON DUPLICATE KEY UPDATE id = id`）；
- 前端按 `serverMsgId` 去重 + 按 timestamp 排序。

**诚实的边界**：
- 是 **at-least-once**，不是 exactly-once；
- **Redis 自身若丢数据（RDB 快照间隔内宕机），已 ACK 但未落 MySQL 的消息会丢**——这是当前架构的真实风险点。缓解方案：开 AOF `everysec` + 主从，或把 ACK 时点后移到 MySQL 落库（但会牺牲延迟）。

### 9.5 【一致性】Redis 和 MySQL 不一致怎么办？

按数据类型区分策略：

| 数据 | 策略 | 理由 |
| --- | --- | --- |
| 消息 | 最终一致，容忍 <1s 窗口 | 用户感知不到 |
| 好友/群成员 | **MySQL 为准 + 缓存重建**，关键操作顺序不对称（见 5.7） | 鉴权依赖，必须准 |
| 点赞 | Redis 即时可读，异步镜像 MySQL | `GetMomentLikers` **从 Redis 读**（`:316-319`），因为点赞写入 Redis 后立即可见，MySQL 是异步的 |
| 未读 | Redis 为真相源（`convSync` 覆盖前端） | 高频写 |

**热点 key 的问题**：`unread:{uid}`、`inbox_order:{uid}` 是 per-user 的，热点分散；但 `group_seq:{gid}` 是大群热点（每条消息 `INCR` 一次）。**这是 Redis Cluster 下会 CROSSSLOT 的原因**（`消息链路改造设计.md:118`）：群聊一次 Lua 要更新多个用户 key，在 Cluster 下分布在不同 slot，会报错。**当前只支持 Standalone/主从。**

### 9.6 【消息 ID】为什么不用全局自增计数器？

见 3.3 第 1 点。核心是 **BUG-004**：Redis 计数器重置会与 MySQL 已有主键冲突。

补充风险分析：
- 时间型 ID 依赖**时钟**——如果 Redis 服务器时钟回拨，可能产生**比已有 ID 更小**的新 ID → 主键冲突。当前没有防护（可以用 `max(now, last_ts)` 的 Lua 逻辑加上）。
- 单毫秒 999 条上限，超过直接 `redis.error_reply`。对单群来说够用（28000 QPS 全局，但单毫秒不可能 999 条）。

### 9.7 【面试题】群聊未读为什么要改成水位线？

完整答案见 4.3。要点是**三个动机**（语义精确、消除 O(N) 写放大、补齐半实现）+ **两个工程细节**（协议可选字段向后兼容、迁移顺序的数学正确性）。

**如果被追问「迁移期间怎么保证不出错」**：答案是「先迁移、后发布」的顺序 + `read_pos_init = seq − unread` 的数学恒等式，加上真实 Redis 的集成测试验证（`redis_repo_integration_test.go:104-133`）。

### 9.8 【场景题】一条消息要推给 10 万人怎么办？

当前架构的答案：

1. **群上限 500**（`group_service.go:28` `maxGroupMembers = 500`），所以不存在这个问题——但这是**产品限制而非技术方案**；
2. 群聊**不写扩散**（只写 1 份 outbox），所以发送路径本身与群规模无关（除了 Lua 里遍历成员更新会话摘要那部分）；
3. **推送**是主要瓶颈：relay 会遍历 `Recipients` 逐个 push。10 万人需要改造。

**改进方向**（面试可答）：
- **只推在线成员**：维护 `online_users:{gid}` Set，推送时只扫在线子集（`群聊未读水位线改造方案.md:120` 已列为后续项）；
- **分层推送**：把 fanout 拆成独立消费者，按群分片；
- **拉模式**：大群完全用拉（客户端定时/长轮询），或参考 Feed 的「大V」策略做混合。

### 9.9 【Go 语言】项目里的 Go 特性和陷阱

| 主题 | 位置 | 要点 |
| --- | --- | --- |
| `sync.Map` | `conn/manager.go:11` | 读多写少的连接表；但**类型断言 `val.(*ClientConnection)` 无 comma-ok**（`:31`）——存入非该类型会 panic |

### 9.10 【工程】这个项目最大的技术亮点是什么？

建议这样组织答案（三层递进）：

1. **架构层**：Redis 作为消息读写主模型 + Redis Stream 作为可靠中转 + MQ 只负责落库的窄职责设计。用「三种成功」的模型清晰区分了可靠性边界。
2. **可靠性层**：`acks=all` 写入确认作为 commit point、Stream 的 XAUTOCLAIM 接管、失败待办的「先写待办再摘除」顺序、成功后才提交 offset、retry Topic 延迟重试、MySQL 主键 + 内容比对的幂等。
3. **性能层**：Lua 原子化把 5 次往返压成 1 次、群聊不写扩散、未读水位线消除 O(N) 写放大、点赞批量削峰（1000 次写 → 2 条 SQL）。

**加上一个自我批评**：一致性依赖 Redis 持久化配置，而当前部署用的是默认 RDB，这是需要改进的地方。

### 10.1 🔴 黑名单功能实际不生效（功能性 Bug）

**现象**：`BlockUser` 只写 MySQL（`service/friend_service.go:397`），**从未写 Redis**。

**证据**：
- 发送鉴权的 Lua 读的是 Redis：`lua_message_write.go:48` → `SISMEMBER KEYS[3] sender`，`KEYS[3] = blacklist:{receiverID}`（`:184`）。
- 全仓库搜索 `SAdd.*blacklist`：**唯一命中在测试文件** `redis/lua_test.go:96`。
- `BlockUser`/`UnblockUser` 里没有任何 Redis 调用（`friend_service.go:383-421`）。

**后果**：`redis.call('SISMEMBER', 'blacklist:...')` 永远返回 0 ⇒ **拉黑后对方仍然能给你发消息**。

**为什么联调没发现？** `docs/前后端联调实施计划.md:235` 的验收项写的是「拉黑后**私聊和再次申请被拒绝**」。这两件事走的是**不同代码路径**：

| 子功能 | 校验位置 | 是否生效 |
| --- | --- | --- |
| 再次发起好友申请被拒 | `SendFriendRequest` 查 **MySQL** `IsBlocked`（`friend_service.go:81-94`） | ✅ 生效 |
| **发私聊消息被拒** | Lua 查 **Redis** `SISMEMBER blacklist:{receiver}`（`lua_message_write.go:48`） | ❌ **不生效** |

验收项把两件事写在一行、合并打勾，**「申请被拒」通过就掩盖了「私聊未被拒」**。这是一个很典型的**验收用例粒度太粗**导致的漏测。

**注意**：前端 `useFriends.ts:46` 会把 `is_blocked` 映射成 `isBlocked` 并用于 UI（如 `GroupManagement.tsx:126` 过滤候选成员），所以**界面上「已拉黑」状态是正确的**——错的是服务端的消息拦截。这也解释了为什么联调时看不出问题。

**这是 P1 级缺陷**（拉黑是用户可感知的安全承诺），但 `问题反馈记录.md` 与 `前后端联调问题记录.md` 都**没有登记**。

**修复方向**：`BlockUser` 里 `SAdd blacklist:{userID} {blockedID}`、`UnblockUser` 里 `SRem`；并让缓存的写失败导致整个操作失败（与群成员移除同理，见 5.7）。另外应把验收项拆成两条独立用例。

> **面试时怎么用这个发现**：不要一上来就说「发现一个 P1」。可以这样说：「我注意到拉黑功能横跨两条路径——申请校验走 MySQL、消息校验走 Redis Lua。我顺着 Lua 的 key 反查写入方，发现 `blacklist:` 只在测试里被写入过。这说明联调验收把两个不同路径的断言合并成了一行，导致漏测。」**展示的是「顺着数据流的 key 反查写入方」这种排查方法，而不是单纯报 Bug。**

### 10.2 🔴 群禁言功能实际不生效

**现象**：Lua 读 `group_member_info:{gid}` 的 `muted` 字段（`lua_message_write.go:114-118`），但**没有任何 service 方法会写这个字段**。

**证据**：
- `SetGroupMemberInfo`（`repository/message_pipeline.go:77-83`）是唯一的写入点，但**全仓库无任何调用方**（只有接口声明 `:45`）。
- `GroupHandler.RegisterRoutes`（`group_handler.go:507-519`）共 10 条路由，**没有任何禁言/解禁接口**（已 grep `mute|Mute|muted` 确认零命中）。
- `WarmGroupMembers`（`:61-75`）会正确地从 `MutedUntil` 计算 `muted`，但它只在「Lua 报 NotMember 后的缓存修复」路径被调用（`msg_service.go:179`）；正常入群走的是 `AddGroupMemberRedis`，其中硬编码了 `{"role":0,"muted":false}`（`redis_repo.go:488`）。

**后果**：禁言状态**无法通过任何 API 设置**，即使手工改了 MySQL 的 `muted_until`，Lua 也读不到（Redis 里恒为 `muted:false`）。**Lua 里的禁言校验（`lua_message_write.go:114-118`）目前是永不触发的死逻辑。**

**注意**：`model.GroupMember.MutedUntil` 字段、`group_member_info` 的 `muted` 字段、Lua 的校验分支、`SetGroupMemberInfo` 方法**全都存在且实现正确**——缺的只是「把它接到 HTTP 接口上」这一步。这是典型的**后端能力已就绪但未暴露**。

**修复方向**：新增 `PUT /group/:id/member/:uid/mute`（owner/admin），内部调 `SetGroupMemberInfo` + 写 MySQL `muted_until`；并把 `AddGroupMemberRedis` 的硬编码改为从 `MutedUntil` 计算。

### 10.3 🟠 撤回路径与新存储结构不匹配（设计遗留）

**现象**：`luaRevokeMsg` 操作的是**旧结构** `inbox:{uid}` / `outbox:{gid}`（`lua_revoke_msg.go:48,64,77`），而当前主路径写入的是**新结构** `inbox_order` + `inbox_data`。

**证据**：
- 写入：Lua 同时写新结构（`lua_message_write.go:81-90`）和旧结构（`:85-86`）；
- 读取：`readIndexedMessages` 读新结构（`redis_repo.go:139-141`），**优先走新结构**；
- 撤回：只改旧结构（`lua_revoke_msg.go:40-41` 的 `ZREM`/`ZADD` 都作用于传入的 key，即 `inbox:{uid}`）。

**后果分析**：由于写入时**双写**了新旧结构，撤回改旧结构后：
- 客户端从**新结构**读取（`readIndexedMessages`）→ **看到的是未撤回的原文**；
- 只有当 `inbox_order:{uid}` 不存在（纯旧数据）时才回退到旧结构。

**这意味着撤回可能对当前主路径不生效**。`lua_test.go:345-405` 的撤回测试**直接向旧结构 `inbox:` 写种子数据**，所以测试通过，但**没有覆盖新结构下的撤回**。

**这是一个测试盲区导致的潜在 Bug**，值得在面试中作为「我发现了一个测试覆盖不到的场景」来讲。

**修复方向**：撤回 Lua 需要同时更新 `inbox_order`+`inbox_data`（以及群聊的 `outbox_order`+`outbox_data`），或者统一收敛到单一结构。

### 10.4 🟠 群成员踢出的 WS 通知不生效

**现象**：`GroupService.KickMember`（`group_service.go:252-280`）尝试通过 `tryGetSendCh(client)` 拿发送通道，但 `tryGetSendCh` 要求客户端实现 `GetSendCh() chan []byte` 接口（`:284-293`），而 `conn.ClientConnection` **只有导出的字段 `SendCh`，没有 `GetSendCh()` 方法**。

**后果**：`tryGetSendCh` **永远返回 false**，`KickMember` 的通知逻辑是死代码。

**补充**：实际踢人走的是 `GroupHandler.RemoveMember`（`group_handler.go:338-346`），它**直接访问 `client.SendCh`**，所以「被移除者收到 groupRemoved 通知」这条链路是**能工作的**（INT-030 已验证）。`KickMember` 本身也**没有任何调用方**（只在 service 内定义）。

**结论**：`KickMember` 是**未接线 + 实现有缺陷**的死代码，应删除或修复。

## 11. 压测数据与工程化

### 11.1 压测结果（`backend/docs/压力测试总结.md`）

环境：单机 Docker（MySQL 8.4 + Redis 7.2 + RabbitMQ 3.13），Go 1.24。**这是迁移到 Kafka 之前的数据，Kafka 版本尚未重新压测。**

**目标 vs 实测**：

| 指标 | 目标 | 实测 | 达成 |
| --- | --- | --- | --- |
| WS 并发连接 | ≥ 10,000 | **50,000** | 500% |
| 消息 QPS | ≥ 5,000 | **28,000** | 560% |
| P99 延迟 | ≤ 100ms | **0.47ms** | 212× 优于目标 |
| goroutine 泄漏 | 无 | 线性增长（每连接精确 +2） | ✅ |

**长连接保持**（`:58-71`）：

| 同时在线 | goroutine 总数 | 成功率 | 瓶颈 |
| --- | --- | --- | --- |
| 1,000 | 2,018 | 100% | — |
| 10,000 | 20,018 | 100% | — |
| 28,000 | 56,018 | 100% | 客户端临时端口池（32768–60999） |
| 50,000 | 100,008 | 100% | 系统综合极限 |

**每连接精确 2 个 goroutine**（ReadPump + WritePump）——**零泄漏**这个结论对整个双 goroutine 模型是很好的验证。

**消息 QPS**（`:94-100`）：

| 连接数 | QPS | P50 | P95 | P99 | 成功率 |
| --- | --- | --- | --- | --- | --- |
| 10 | 29,532 | 0.23ms | 0.38ms | 0.47ms | 100% |
| 100 | 28,993 | 1.70ms | 2.71ms | 3.70ms | 99.96% |
| 1,000 | 27,432 | 18.73ms | 25.04ms | 577ms | 99.58% |

**瓶颈分析（这段最有面试价值）**：

- **QPS 不随连接数增长**（10 连接和 1000 连接都在 27K–30K）⇒ **瓶颈在 Redis 单线程，不在连接调度**。这是很干净的实验设计——通过「改变并发度但 QPS 不变」来定位瓶颈。
- 延迟随连接数恶化：P50 从 0.23ms → 18.73ms，P99 → 577ms。**1000 连接时每个连接都在排队等 Redis。**
- 少量失败来自 `PublishWithContext` 在 RabbitMQ 堆积时阻塞最多 5s（Kafka 版本对应的是 `WriteMessages` 的 5s 超时，重新压测时需关注 `acks=all` 同步写入的延迟）。

**注意**：这份压测是在**旧链路**（v1，同步 publish）下标定的，因为 `消息链路改造设计.md:85,224` 把「压测不同群规模下 Lua 执行耗时」列为**尚未完成的阶段三任务**。**面试时不要说「新链路压测过了」。**

### 11.3 生产部署与运维

**Dockerfile 三段构建**（`Dockerfile`）：

```
node:24-alpine   → npm ci && npm run build → /src/frontend/dist
golang:1.24-alpine → go build -trimpath -ldflags="-s -w" → /out/goim-server
alpine:3.21      → 非 root 用户 goim，拷贝二进制 + 配置 + dist
                   HEALTHCHECK curl /health，ENTRYPOINT ["./goim-server", "-c", "configs/config.yaml"]
```

**前后端打包进同一个镜像**：Go 进程同时提供 API、WS 和 SPA 静态资源（`main.go:336-354`）。

**SPA fallback 的处理**（`main.go:346-353`）：

```go
r.NoRoute(func(c *gin.Context) {
    path := c.Request.URL.Path
    if strings.HasPrefix(path, "/api/") || strings.HasPrefix(path, "/ws") {
        c.JSON(http.StatusNotFound, gin.H{"code": 404, "message": "not found"})
        return
    }
    c.File(frontendDir + "/index.html")
})
```

**API/WS 路径返回 JSON 404，其余返回 index.html** —— 这样前端路由（`/app/chats/xxx`）刷新不会 404，同时 API 拼错路径能得到明确的 JSON 错误而不是一段 HTML。**这是很正确的 SPA 部署细节。**

**Watchdog 双保险**（`deploy/goim-watchdog.sh` + `.timer`）：

- systemd timer 每 30 秒跑一次 `/ready` 健康检查；
- **连续失败 2 次**才 `docker restart`（避免瞬时抖动误重启）；
- 用 state file 计数，成功即清除。

定位：Kafka 版本服务不再因 MQ 断连退出（见 2.2），而是由 `/ready` 返回 503 反映不可用，watchdog 连续检测到 `/ready` 失败才重启容器，用来兜底「进程还活着但服务长时间不可用」的情况。RabbitMQ 版本里它是「NotifyClose 自动退出机制之外的第二道保险」。

**生产 compose**（`deploy/docker-compose.prod.yaml`）与本地差异：
- 用 `APP_IMAGE` 指向 GHCR 镜像，`depends_on` 带 `condition: service_healthy`；
- 全部服务加 `deploy.resources.limits.cpus: "2.0"`；
- 用 `uploads_data` volume 持久化上传目录；
- 敏感配置全部走环境变量 `${VAR:?Set VAR}`（**`:?` 语法让变量缺失时直接失败**，避免用默认密码启动）。

- [ ] 一句话架构主张：「Redis 是读写主模型，MySQL 是异步归档，MQ 负责可靠解耦」
