# 运行修复记录

日期：2026-09-29

## 目标与设计约束

目标是按仓库的本地开发方式启动 MySQL、Redis、Kafka、Go 服务和前端，并通过真实 HTTP/API/WebSocket 路径确认可用。

本次修复遵循现有设计：入口采用手工显式装配；聊天消息以 Redis 原子写入和 Stream 为主路径，经独立 Kafka Writer 的 relay 投递后异步归档到 MySQL；`message.atomic_pipeline` 保留旧链路回退开关；Kafka 故障通过 `/ready` 表示，进程保留自动重连能力。

## 发现与处理

| 发现 | 复现或证据 | 处理 |
| --- | --- | --- |
| 后端入口缺失 | `go run ./cmd/server -c configs/config.local.yaml` 报 `directory not found`；README、Dockerfile 和架构文档都要求该入口 | 新建 `backend/cmd/server/main.go`，按现有服务构造器显式装配依赖、路由、消费者和 relay |
| Go 依赖校验记录不完整 | `go build ./internal/...` 报 Kafka 模块缺少 `go.sum` 记录 | 执行 `go mod tidy`，使内部包和入口可编译 |
| Docker 镜像站拒绝 Kafka 镜像 | `docker compose up -d` 拉取 `bitnami/kafka:3.7` 时返回 403 | 本地和生产 Compose 改用可拉取的 `apache/kafka:3.7.0`；按 [Apache 单节点 KRaft 示例](https://github.com/apache/kafka/blob/trunk/docker/examples/docker-compose-files/single-node/plaintext/docker-compose.yml)映射环境变量、监听器与持久化目录 |
| 本机现有容器占用默认端口 | Docker 已运行的其他 MySQL、Redis 容器占用 13306、16379 | 仅在忽略的本地 `.env` 和 `config.local.yaml` 中改用 23306、26379、29092、28081，避免改动其他项目 |
| `.gitignore` 把入口目录一并忽略 | 通配规则 `server` 命中 `backend/cmd/server/main.go` | 移除过宽规则，保留只针对 `backend/server` 可执行文件的规则 |
| 缺少一条对实际运行链路的快速回归检查 | 原 E2E 的 `TestMain` 使用旧消息服务构造器 | 增加 `scripts/smoke.mjs`，覆盖运行中的原子消息链路和异步归档 |

## 验证结果

- `go build ./internal/...`、`go build ./cmd/server`：通过。
- `npm run build`：通过；Vite 页面返回 HTTP 200，浏览器注册新用户后进入聊天界面，控制台无错误。
- `docker compose up -d --quiet-pull`：通过；MySQL、Redis、Kafka 为 `healthy`，Kafka UI 返回 HTTP 200。
- Go 服务 `/health`、`/ready` 和 Swagger：均返回 HTTP 200；后端打包后的 SPA 页面返回 HTTP 200。
- `node scripts/smoke.mjs`：通过。验证注册、登录、加好友、WebSocket 消息投递和 `serverAck`，并从 MySQL 搜索到归档消息。
- `docker build -t goim:local .`：通过。镜像单实例运行时健康检查为 `healthy`，`node scripts/smoke.mjs http://127.0.0.1:18082` 通过。
- `docker compose -f deploy/docker-compose.prod.yaml config --quiet`：通过（使用本地占位环境变量检查语法）。
- `git diff --check`：通过。

当前保留运行中的本地开发服务：前端 `http://127.0.0.1:5173`，Go 后端 `http://127.0.0.1:18080`，Kafka UI `http://127.0.0.1:28081`。端口覆盖保存在本机忽略文件中，仓库默认端口没有改变。冒烟脚本创建的 `smoke_*` 测试用户和消息保留在本项目的本地数据库卷中。

## 另一个观察

并行运行宿主机后端和一体镜像时，镜像侧的 `serverAck` 曾超时；关闭宿主机后，同一镜像的完整冒烟检查立即通过。现有 relay 使用共享 Redis Stream 消费组，但确认和推送只查本进程的 `ConnectionManager`。事件如果被另一实例取走，连接所在实例就收不到实时回执。这个问题不影响上述单实例运行结果；多实例部署需另行设计跨实例推送或按连接归属路由，不能仅依赖粘性会话。

前端依赖安装时 npm 报告 7 个依赖安全告警（2 个中危、5 个高危）；它们没有阻止本次启动和构建，尚未进行依赖升级。

## 审查重点

1. `backend/cmd/server/main.go` 是否与现有 Redis 优先、Kafka 异步归档链路一致。
2. Compose 的 Kafka 镜像和 KRaft 监听地址是否同时适合容器内、宿主机访问。
3. 多实例实时推送的既有设计限制是否纳入下一轮修复。
