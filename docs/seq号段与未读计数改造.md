# seq 号段、实际未读计数与首次历史加载

## 最终实施计划

1. 在现有 `conversations` 增加 `seq_alloc_max`，不新建号段表。
2. 使用 MySQL 事务预留号段，提交成功后在内存取号，默认每段 1000。
3. 保留会话锁覆盖“取号 → 同步写 Kafka”，适配已读、清空、删除会话和入群边界。
4. 未读直接批量统计有效消息，不使用 seq 差值，也没有 1000 条校正上限。
5. 首次通过 HTTP 获取最新 50 条实际历史消息，上滑以最旧消息 seq 向前分页。
6. 增量补拉保留现有区间协议，空页继续，按返回的 toSeq 推进。
7. 增加数据库迁移、回归测试，并在独立 MySQL 中验证事务取号。

## 分配与边界

`conversations.max_seq` 是实际已落库的最大 seq；`seq_alloc_max` 是已预留的号段上限。预留到 1000、实际发送到 12 时，清空记录和入群边界使用实际位置 12，不能使用 1000。

换段时在短事务内确保会话行存在、加行锁、推进 `seq_alloc_max`。首次读取旧 Redis `seq:{convId}` 作为迁移下限，此后不再更新旧计数器。段内分配不访问数据库；重启后剩余号码放弃，新号段从持久化上限之后开始。事务提交失败或结果不确定时不使用返回的候选号段，重试重新申请。

实际分配位置保存在进程内，与 MySQL 已落库位置合并后用于边界操作。清空、删除会话、已读确认与入群边界和发送使用相同的会话锁。消息落库更新摘要和 max_seq 时保留 seq_alloc_max。

本版本按单个消息写入服务实例部署。数据库能保证并发预留的号段不重叠，但多个服务分别持有同一会话号段时，仍不能保证 seq 与 Kafka 日志顺序一致；多实例会话归属和旧写入者隔离不在本轮范围内。

配置：

```yaml
message:
  seq_segment_size: 1000
```

## 未读与分页

未读从 MySQL 批量 COUNT 实际消息：位于已读位置之后、可见下界以内的有效他人消息，排除撤回通知、已撤回消息和个人删除。查询失败返回错误，不退回 seq 差值。服务端未读随异步落库更新；前端实时逐条增减，由 convSync 校准。

首次收到会话同步后，调用 `/conversations/:convId/messages?beforeSeq=0&limit=50`。历史查询在 LIMIT 之前过滤个人删除，额外取一条判断 hasMore，返回结果按 seq 升序。初始窗口期间的实时推送继续合并；窗口返回后，以窗口最新 seq 为同步起点，补拉期间新增的消息。重连保留已初始化的游标；过期连接的 HTTP 响应不会写入新连接的状态。

历史游标单独保存原始分页结果的最小 seq，包含不会渲染为聊天气泡的撤回通知；不会因一页全是通知而反复请求同一页。

增量补拉仍以 100 个 seq 为一个区间，hasMore=true 时继续，空页不结束。大空洞可能带来额外请求，按实际消息条数做正向分页留待后续优化。补拉水位使用 MySQL 已落库的最大 seq。

## 消息消费改造计划

1. 沿用 `msg_topic` 和 `msg-persist` 的消费进度。由该组逐条消费，每条单独提交 MySQL 事务，随后尝试更新 Redis 并推送。切换时停止独立的 `msg-deliver` 组。
2. 数据库写入失败时，在当前事件退避重试，恢复后继续消费。格式错误和唯一键冲突转入死信。已落库消息的在线投递失败时，接收方可从 MySQL 补拉。
3. 会话列表的最大 seq、补拉水位和补拉内容以 MySQL 为准。Kafka offset 重放时读取已落库的消息状态，保留已撤回的状态。发送端仍在 Kafka 确认后收到 `serverAck`。
4. 验证收到推送后立即可查历史、数据库失败时停止推进、Redis 领先时补拉水位保持在已落库位置。

逐条写入移除了等待攒批的时间，同时增加了 MySQL 事务次数。数据库失败会暂停该 Reader 的消费进度，直到当前消息写入成功。切换前暂停发送并排空旧消费链路，沿用原 `msg-persist` group ID。已经被旧客户端游标跨过的消息需要重新加载历史，旧死信也需要单独核查。

## 升级步骤

1. 暂停旧服务发送入口，等待在途 Kafka 写入结束，确认 persist 和 deliver 消费追平并处理相关死信。确保旧写入实例停止且不会自动恢复。
2. 对已有数据库执行 `backend/scripts/migrations/016_conversation_seq_segments.sql`。脚本新增字段，将初值设为会话 max_seq 与 messages 最大 seq 的较大值。已有数据库不会因更新 Compose 自动执行初始化目录里的新脚本，需要显式迁移。
3. 保留旧 Redis `seq:*` 键。新进程首次为每个会话申请号段时，将旧计数器作为额外下限，原子写入 seq_alloc_max；不要在导入前清理旧键。
4. 启动新版本单个写入实例，再开放发送。历史消息 seq、用户 read_seq 不重编号，不迁移未读计数。
5. 保留新增列及其上限。不要直接启动旧 Redis 分配器回滚；若需回滚，需再次暂停和排空，将旧计数器推进到至少 seq_alloc_max，且禁止旧进程使用残留状态。

本次只提供迁移脚本和实现，不自动修改现有运行中的业务数据库。

## 验证

- Go 服务测试覆盖取号并发顺序、换段、重启、旧计数器下限、申请失败、发送失败、清空/已读/删除边界和跨空洞历史分页。
- MySQL 集成测试覆盖号段持久化、并发预留不重叠、消息摘要更新保留上限、实际未读过滤和历史个人删除过滤。
- 前端测试覆盖最近 50 条实际消息、请求期间实时推送、落库滞后的空窗口、重连增量补拉和空页继续。

运行 MySQL 集成测试需要设置 `GOIM_TEST_MYSQL_DSN`，指向允许创建临时数据库的测试实例。测试创建独立临时数据库并在结束时清理。
